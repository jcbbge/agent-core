## Contracts and merge tags

**Original intent.** Merge tags, document→build binding, and section
optionality — with a mirror-faithful namespace so tags carry HubSpot's own
property paths and Arc never renames across that boundary.

**What changed.** The merge-tag vocabulary was hard-cut to mirror-faithful
`deal.*` / `contact.*` paths. New package `packages/contracts/merge-tags` holds
`tag-whitelist.ts` — the authoritative enumerable registry for Toolbar,
resolver validation, and agent tooling. Alongside: subsection addressing, an
unknown-builder chip, path-aware finalize, `contract_versions` bound to
`build_id`, and a fix where signed-document image URLs refresh on read.

**What it solves.** The vocabulary previously lived in three places (Toolbar,
resolver, author memory) and could drift — a tag could appear in the picker and
fail to resolve. Presigned image URLs were expiring on old signed documents.

**Where it sits.** Between the TipTap editor and the API resolver registry.
The whitelist also declares `DEFAULT_BUILDER_SECTION_KEYS` (venue, catering,
rentals, vendors, additional_labor) — the join between merge tags and the
Build's section model.

**Trajectory.** `{{builder.catering}}` / `{{builder.vendors}}` now have a home
to resolve into; they light up when the Galley read arrow is fully consumed by
UI. Seam: documents ↔ builds.

## Galley data plane

**Original intent.** Mirror Galley's catering data into Arc and build the
menu-plan write-back — single write surface, approve as the reconciliation gate.

**What changed.** The existing mirror targeted the wrong Galley primitive
(`Menu`); sync, Electric DDL, and tests retargeted to `MenuPlan`. Migration
0059 built a nested three-level mirror: `galley_menu_plan_events` →
`…_item_groups` → `…_event_items`. Recipe read-arrow stamps `galley_recipe_id`
and snapshots. Write-arrow substrate landed: allowlist + `mutateAndEnqueue`.
`approveMenuPlanEvent` was added to the allowlist **with no UI**.

**What it solves.** Arc could read recipes but had no representation of a
*menu plan for an event* — the actual unit catering is planned in. Without it,
nothing for a catering section to attach to.

**Where it sits.** Galley schema in `packages/db` → Electric shapes → PGlite
client reads. Writes go through allowlist + write-ledger (write arrow of the
four-arrow architecture).

**Trajectory.** Foundation of the Galley mini-client wave. Approve being
allowlisted-but-unwired is intentional: capability proven, gate shut until
reconciliation semantics are ruled.

## Multi-location inventory

**Original intent.** Location as a *scope*, not a deployment — per-location
par, counts, and ordering. Spec material for the ops meeting (STG-647).

**What changed.** The 662-line locations spec landed, then three migrations:
0061 (par / sort_order / unit_label / **`inventory_counts`**), 0062 (quantity
widen to `numeric(12,4)`), 0064 (walk tokens/sessions). On top: authenticated
count walk UI (`CountWalkShell` POSTs counts), location rollup, and the R-8
ruling — walk token exchanged for a scoped session rather than acting as a
long-lived credential.

**What it solves.** Nathaniel's team runs per-location PAR sheets with
fractional pack units (3.5 cases). Schema previously: integer quantity, no par
column, `stock_locations` name-only.

**Where it sits.** `catalog_item_allocations` is the location-scoped join. Walk
auth reuses the portal-token *pattern* but hardens into token-for-session
exchange. Counts are append-only via a plain-mirror API (not optimisticMutate).

**Trajectory.** Capture path exists end-to-end. Next product value is
**restock = count − par** grouped by `order_source` (order drafts), plus the
historical worksheet importer — not another ledger table.

**Honest correction vs earlier briefing.** A prior seed claimed the
`inventory_counts` ledger was missing. It is present in 0061. Do not rebuild it.

## Portal client auth

**Original intent.** Reverse the standing "portal is pure-public" law and give
the portal real client accounts (operator-signed).

**What changed.** Superseding ADR + contradiction sweep; migration 0060
(`client_accounts`, `client_sessions`, `client_deal_access`);
`requireClientAuth`; registration/login; portal shell; staff view-as-client
with **server-side refusal**; migration 0063 binding `client_account_id` onto
`signature_records` and `actor_client_account_id` onto `contract_events`.

**What it solves.** A signature previously had no durable identity behind it —
someone with a link signed something. Now a signature carries *who* signed.
Access is scoped per deal rather than per naked link.

**Where it sits.** A second, deliberately siloed auth realm beside staff Google
OIDC. `requireClientAuth` is the boundary. View-as refuses on the server so a
staff member cannot reach client data by guessing a URL.

**Trajectory.** If the portal later relocates into a planning app, this
identity binding is the historic-home load-bearing piece — carry it forward;
do not re-derive client sessions.
